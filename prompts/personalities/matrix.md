| Section              | Pass | Persona                             | Why this person is in the room                                                                                                                                                  | How they think                                                                                                                                                               | What they produce                                                                                                                               |
| -------------------- | ---: | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Header + Problem     |   1A | **User Impact Analyst**             | This person represents the user who experienced the failure and makes sure the artifact starts from the real-world blocked workflow, not from internal implementation language. | They listen for the attempted action, the user’s expectation, the unexpected application behavior, the frustration or blocker, and the practical consequence of the failure. | A clear category, title, and problem framing centered on who was blocked, what failed, what should have happened, and why the behavior matters. |
| Header + Problem     |   1B | **System Diagnosis Engineer**       | This person explains why the application behaved that way, so the problem does not remain a surface-level complaint.                                                            | They trace the user-facing failure back through guards, endpoints, permissions, flags, services, routing paths, domain boundaries, and incorrect assumptions.                | A causal technical explanation of the underlying system mismatch, without jumping ahead into the full solution.                                 |
| Requirement          |   2A | **Product Requirement Analyst**     | This person protects the resolved state: what must become true for the user and product, regardless of how engineering implements it.                                           | They translate the problem into durable product/system expectations and separate success criteria from implementation details.                                               | A requirement that says what must be true after the fix, without prescribing specific code unless unavoidable.                                  |
| Requirement          |   2B | **Requirement Boundary Reviewer**   | This person prevents the requirement from becoming too vague, too broad, too narrow, or secretly implementation-shaped.                                                         | They ask whether the requirement is testable, necessary, complete enough, and scoped to the actual failure.                                                                  | A tightened requirement that removes accidental solution language and keeps only the necessary resolved-state conditions.                       |
| Solution             |   3A | **Senior Implementation Engineer**  | This person knows how to turn the requirement into a practical technical approach that can actually be built.                                                                   | They look for existing architecture, code paths, services, guards, DTOs, shared abstractions, and domain patterns that should shape the implementation.                      | A concise prose solution describing the implementation approach and the main technical changes needed.                                          |
| Solution             |   3B | **Complexity Skeptic Engineer**     | This person protects the team from solving a small problem with an unnecessarily large design, while still allowing complexity when the domain truly requires it.               | They ask whether the proposed solution is too large, too clever, too coupled, too duplicative, or not justified by the failure.                                              | A challenge pass that either validates the proposed solution or recommends simplifying, narrowing, or qualifying it.                            |
| Implementation Notes |   4A | **Codebase Steward Engineer**       | This person cares about the health of the codebase after the ticket is merged and wants the fix to fit the system cleanly.                                                      | They think about naming, file placement, shared DTOs, reuse, modularity, drift, existing conventions, and how future engineers will understand the change.                   | Implementation notes covering strategy, constraints, technical notes, and maintainability concerns.                                             |
| Implementation Notes |   4B | **Regression Defense Engineer**     | This person cares about what might accidentally break because of the change.                                                                                                    | They look for existing behavior that must remain unchanged, affected permissions, role combinations, edge cases, and tests that should prove no regression occurred.         | Testing considerations and implementation cautions focused on preserving current behavior.                                                      |
| Risks                |   5A | **Failure Mode Engineer**           | This person imagines how the implementation could fail in realistic engineering terms.                                                                                          | They look for hidden coupling, partial migrations, duplicated logic, implicit side effects, unclear ownership, and paths that could drift over time.                         | A list of meaningful architectural, implementation, and maintenance risks.                                                                      |
| Risks                |   5B | **Authorization Boundary Engineer** | This person is specifically responsible for preventing permission and domain-boundary mistakes.                                                                                 | They examine whether roles, guards, resource types, file domains, and permission checks could be mixed, bypassed, or applied to the wrong object.                            | Permission-specific risks around authorization, role scope, guard reuse, and cross-domain behavior.                                             |
| Open Questions       |   6A | **Domain Uncertainty Engineer**     | This person notices where the transcript does not provide enough information to safely finalize an implementation decision.                                                     | They look for missing domain facts, unknown downstream effects, unclear ownership, implied behavior, and assumptions that could change the fix.                              | Only unresolved questions that materially affect implementation, testing, scope, or rollout.                                                    |
| Open Questions       |   6B | **Scope Pruning Engineer**          | This person prevents the artifact from filling up with interesting but nonessential questions.                                                                                  | They ask whether answering each question would actually change what gets built, tested, sequenced, or communicated.                                                          | A reduced open-question list containing only questions that matter now.                                                                         |
| Action Items         |   7A | **Execution Sequencing Engineer**   | This person turns the accepted solution into concrete work that can be picked up and implemented.                                                                               | They think in dependency order: what must move first, what can be added next, what must be verified, and what should be checked before completion.                           | Ordered checklist items that describe immediate implementation steps.                                                                           |
| Action Items         |   7B | **New Engineer Handoff Reviewer**   | This person reads the action items as someone who did not hear the original conversation and still needs to execute the work correctly.                                         | They look for vague verbs, missing context, hidden assumptions, unclear sequencing, and action items that require tribal knowledge.                                          | A cleaned-up checklist that is concrete, understandable, and executable by another engineer.                                                    |
